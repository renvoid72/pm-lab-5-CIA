# План управления качеством

Версия: 1.0 · Дата: 23.11.2026 · Ответственный за качество: Ковальчук В.

## 1. Что для нас качество

Качественный результат для заказчика — воспроизводимый расчёт опасных участков ДТП с привязкой к дорогам, быстрая и адаптивная интерактивная карта с корректной атрибуцией источников и отчёты без расхождений в цифрах.

Требования к качеству из `docs/requirements.md`:
- **NFR-01**: карта открывается быстрее чем за 3 секунд (Lighthouse, Slow 4G).
- **NFR-02**: интерфейс корректно работает на экранах от 360 px (DevTools браузера).
- **NFR-03**: выгрузки открываются в стандартных программах (Excel, PDF).
- **NFR-04**: обновление данных и анализ запускаются одной командой без ручной правки.
- **DR-01 – DR-05**: координаты у ≥ 90% записей ДТП (`DR-01`), привязка к дороге ≤ 50 м (`DR-02`), данные за последние 3 года (`DR-03`), на карте видны подпись «© участники OpenStreetMap» и дата (`DR-04`), заполненность `weather` ≥ 80% (`DR-05`).

## 3. Стратегия тестирования

| Уровень | Что проверяем | Инструмент | Автоматически? | Где результат |
|---|---|---|---|---|
| Проверка данных | Структура слоёв, CRS, геометрия, дубликаты, границы, число объектов и атрибуты | `scripts/validate_data.py` (`data/validation.json`) | Да, в CI | Лог GitHub Actions / локальный запуск |
| Модульные тесты | Расчётные функции в `src/` на простых примерах с известным ответом | `pytest`, `tests/` | Да, в CI | Лог GitHub Actions / отчёт `pytest` |
| Приёмка историй | Критерии приёмки историй MVP (`US-1`, `US-2`, `US-3`, `US-5`) и `NFR-01`–`NFR-04`, `DR-04` | Ревью, Lighthouse, DevTools, обзор спринта | Нет (владелец продукта) | Комментарии в PR/Issue и протокол обзора |
| Проверка выводов | Совпадение чисел в отчётах/карте с расчётами и корректность формулировок с учётом ограничений данных | Повторный прогон вторым участником | Нет (ручная сверка) | Ревью PR / заметки к релизу |

Что не тестируем и почему:
- Полный прогон ноутбуков в CI не выполняется, чтобы не замедлять проверки и не зависеть от внешних сервисов/файлов. Расчётная логика выносится в `src/` и проверяется через `pytest`, а в CI проверяется, что ноутбуки сохранены без вывода ячеек.

## 4. Чек-лист ревью Pull Request

Ревьюер отмечает в PR каждый пункт или пишет замечание.

**Для любого PR**
- [ ] PR связан с задачей (`Closes #N`), ветка и коммиты оформлены по правилам
- [ ] Автопроверка CI зелёная, у PR проставлена метка

**Код и ноутбуки**
- [ ] Новые расчётные функции вынесены в `src/` и покрыты тестами с известным ответом
- [ ] Ноутбуки сохранены без вывода ячеек и воспроизводятся без ручных правок (`NFR-04`)

**Данные**
- [ ] Расстояния и буферы (в т. ч. привязка ≤ 50 м по `DR-02`) считаются в метрической проекции
- [ ] Слои проходят `scripts/validate_data.py`, сырые данные не попали в Git

**Документы и интерфейс**
- [ ] Цифры в документах и на карте совпадают с расчётами, указаны ограничения данных (`DR-01`, `DR-05`)
- [ ] На карте и в документации есть подпись «© участники OpenStreetMap» и дата (`DR-04`), зафиксировано использование ИИ

## 5. Качество в Definition of Done

Какие пункты плана качества добавлены в `docs/definition-of-done.md`:
- Обязательная зелёная автопроверка CI перед слиянием, наличие метки у PR и тестов с известным результатом для новых расчётных функций.
- Проверка слоёв через `scripts/validate_data.py`, сохранение ноутбуков без вывода ячеек и фиксация атрибуции/ограничений данных.
